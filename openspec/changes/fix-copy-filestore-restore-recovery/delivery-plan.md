## E2E decision

`e2e_required=true`.

The remaining verification gap is cross-component: a real Odoo restore must write/read a file-backed attachment under the checkout-local `data_dir`; PostgreSQL/catalog evidence must retain the same identity; a later verifier failure must survive process/catalog reopen; and public removal must affect only the exact target. Focused unit tests are necessary for exhaustive mismatch cases but cannot prove that integrated Odoo/PostgreSQL/filesystem behavior.

The test repository is the project-description resource `https://gitlab.icode.by/a.maksimchyk/binta-test-repo`. The Tester SHALL use the numbered profile and reference checkout declared by the workspace, a fresh `odcli-N`, a unique HTTP port and target database, and the exact published candidate SDK SHA. The legacy `prepare_numbered_project.py` flow SHALL NOT overwrite the numbered profile. Secrets, private hostnames, and personal data SHALL remain outside Git and evidence.

## Readiness, execution, and cleanup

Before consuming a live attempt, Tester SHALL verify: exact candidate SHA is published; product focused tests and required review gate are complete; the dedicated PostgreSQL cluster is healthy on its configured numbered endpoint; a free `odcli-N`, unique database and ports are selected; the reference checkout is clean; the candidate interpreter, `tests/e2e/render_terminal.py`, and `tests/e2e/fixtures/terminal-font.ttf` are available; and the test script has passed its deterministic lower-level self-checks. Automated local suites are subject to the workspace ten-minute limit; manual agent walkthroughs are not. A run that reaches the automatic limit SHALL be stopped by its exact owned process and continued through exact-head CI rather than split.

For each case, record PASS against the exact product SHA, test-script SHA, fixture identity, slot, database, and port. A new product SHA requires impact assessment and rerun only of affected cases. Cleanup uses `scripts/agent_checkout.py remove <N> --project <numbered-project>` with the same project input, verifies target DB/filestore absence, and verifies the source, backup, shared cluster, unrelated databases/filestores, reference checkout, and primary runtime remain. A failed cleanup is a retained diagnostic state, not permission for broad deletion.
