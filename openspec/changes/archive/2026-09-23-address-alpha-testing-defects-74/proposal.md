## Why

GitHub issue #74 collects the second batch of confirmed alpha-testing defects of OdCLI plus four larger improvement requests submitted alongside them. The eighteen items span foreground lifecycle locking, Git commit formatting in environment worktrees, missing `env rm --force-connections`, false PostgreSQL state reporting, incomplete self-contained project initialization, broken large-backup validation, lost filestore provenance on self-contained restore, an insecure hidden admin password reset, stale remote database name handling, missing long-restore progress, auxiliary Odoo pipe deadlock, truncated `module update` tracebacks, absent VCS revision in `--version`, a new `odcli bug-report` workflow with an agent skill, centralized HTTP/XML-RPC transport, a new `odcli update` self-upgrade flow, removal of low-quality E/F tests, and automatic logfile provisioning for `run --detach`. They are confirmed on current `main`, block normal alpha workflows, and must be planned together because several items share the same lifecycle, transport, and CLI boundary contracts already established by `address-alpha-testing-defects-67`.

## What Changes

- **Foreground `run` does not hold the environment artifact lock while waiting (item 1)**: `run_foreground_command()` enters the shared artifact lock only for atomic spawn/runtime-identity registration and cleanup/revalidation, then releases it before `wait_foreground_process()`. A parallel `stop` can acquire the exclusive lock, read the persisted runtime identity, and call the existing `terminate_pid()`. Foreground stdio, signals, exit code, PID/create-time/process-group validation, and stale-runtime safety are preserved. A live E2E regression enforces the scenario across two real CLI sessions. (server-lifecycle, instance-runtime-binding)
- **`git commit` uses the already-resolved project ticket settings in environment worktrees (item 2)**: the Git resource receives the resolved project settings instead of re-loading `.odcli/project.toml` from the environment worktree root. The ticket URL is appended as the second paragraph whenever the selected project manifest enables `ticket_link_enabled` and `ticket_base_url`, regardless of whether the worktree has its own `.odcli/project.toml`. (odoo-git-workflow)
- **`env rm` exposes `--force-connections` and stops recommending a non-existent option (item 3)**: `odcli env rm` gains `--force-connections`, routed through `EnvironmentManager.remove_command()` into the existing `build_database_drop_command()` with terminate scope limited to the exact COPY database. Without the flag the command stays fail-closed and the error recommends the now-existing `--force-connections` (and `odcli stop` as an alternative that avoids terminating sessions). Protected/default/shared databases and sessions of other databases remain untouched. (development-environment, cli-odcli)
- **`postgres up` and `env list` report truthful PostgreSQL state (item 4)**: `postgres up` builds its diagnostic result from the captured cluster regardless of `Command[None]` returning `None`. The monitor no longer derives `STOPPED` from an empty or unparseable Docker resource snapshot: `stopped` follows only from a successful `PostgresCluster.status_command()`; a metrics failure degrades only metrics and keeps the actual lifecycle state. `stats_failed` no longer implies a stopped cluster. (postgres-cluster, environment-monitor, cli-odcli)
- **`init` produces a complete self-contained project in one command (item 5 + comment)**: `odcli init` gains `--test-url`, `--test-database`, `--test-branch`, and `--local-config`. These fill the existing `[test_instance]`, select generated `.odcli/odoo.conf` as the effective local `source_config`, create `.odcli/.env` with `ODCLI_TEST_INSTANCE_ORIGIN_PINS` and an empty `ODCLI_TEST_MASTER_PASSWORD=` under `0600`, and record `data_dir` as the absolute `{project_root}/.odcli/filestore`. A blocking completeness check lists missing groups before any file write; `test_instance.database` is not a missing group when item 9 can resolve exactly one remote database. Interactive mode offers cancel-vs-partial confirmation (Click confirm, default cancel) when `no_input` is false and output mode is RICH; `--no-input` fails with `init_incomplete` unless `--allow-partial` is explicit. Re-running `init` without test-instance options preserves an existing valid `[test_instance]`. `--dry-run` shows manifest/config/dotenv ActionSteps without writes, secret generation, cluster mutation, or prompts. Interactive mode may prompt hidden for the remote master password; `--no-input` leaves empty `ODCLI_TEST_MASTER_PASSWORD=`. External PostgreSQL/source-config remains a supported full profile when chosen explicitly; missing remote test instance in that profile still requires cancel-vs-partial or `--allow-partial`. Self-contained Compose `init` also creates bootstrap database `tmp` with `base` installed through the same project runtime (`--database tmp --init=base --stop-after-init`), as required by the owner comment on #74. (project-init, cli-odcli, development-environment, database-restore)
- **Backup validation stops rejecting large Odoo archives by hardcoded byte ceilings (item 6)**: remove 512 MiB/2 GiB ceilings; keep 4096 entries and 64 KiB streaming; ratio 100 does not invalidate `dump.sql` alone; reserve `max(1 GiB, 10%)`; operator key `backup.max_uncompressed_bytes`; codes `backup_corrupt`/`backup_unsafe`/`backup_operator_limit`/`backup_insufficient_disk`; version from `version` else `major_version` + `.0`. (backup-catalog)
- **Self-contained restore records and reuses the proven filestore path (item 7)**: full self-contained `init` records one absolute project-owned `data_dir` in generated `.odcli/odoo.conf`. Restore writes that canonical path into the restore binding alongside cluster/database/backup identity. `db rm` deletes only the exact contained non-symlink filestore and returns `deleted` or `absent` with the path. External config without a provable `data_dir` stays fail-closed `unknown`; no directory is deleted by database name or platform default. `doctor` can surface an actionable finding when a restore binding exists without `data_directory`. (database-restore, development-environment)
- **Admin password reset is an explicit secret assignment (item 8)**: the literal `admin` value in the reset flow is replaced by one mandatory secret input. Interactive mode prompts hidden with confirmation; non-interactive mode reads `ODCLI_ADMIN_PASSWORD` through the existing project dotenv/redaction boundary. If the secret is absent, the command fails before any restore/drop mutation. The same mechanism serves `db reset-admin-password`, restore, and COPY replacement. The secret never appears in argv, shell history, manifest, catalog, plan, Rich/JSON/TOON output, logs, or exception text; the result reports only the fact and a safe provenance (`prompt` or `environment`). No implicit fallback to `admin` or any other common value remains. (database-restore, cli-odcli)
- **Remote refresh resolves the test database name when it is not configured (item 9)**: `test_instance.database` becomes optional in the manifest model and parser/writer. If it is explicitly set, it is used without requiring database list availability. If it is absent, remote-refresh preflight obtains names through the existing `DatabaseResource.names()`; exactly one database is selected for the current operation; zero databases and multiple databases produce distinct actionable errors before download; multiple databases list the available names. The auto-detected name is reflected in plan/result and backup provenance but is not written back to `project.toml`. Manifest round-trip does not add `database` when it was not set. (project-init, database-backup, cli-odcli)
- **Long restore shows current stage and activity (item 10)**: the existing `StepObserver`, `StepEvent`, and Rich runner are reused to publish real stages — backup preparation, auxiliary Odoo startup, database restore, created-database verification, filestore restore, requested admin reset, and project default switch — with elapsed time. A heartbeat updates the spinner and elapsed time during blocking actions without child stdout. Percent is shown only when a trustworthy total is known (streaming dump/filestore bytes). On error, the safe primary cause and the last stage are preserved instead of a generic `auxiliary database manager failed readiness`. JSON/TOON keep the existing single-document contract and exit code; terminal progress does not pollute machine stdout. (server-lifecycle, cli-odcli)
- **Auxiliary Odoo does not block on filled stdout/stderr pipes (item 11)**: the process boundary for spawned long-running handles drains `stdout` and `stderr` concurrently and continuously, keeps a bounded redacted tail, and attaches that tail plus the original error type to readiness/startup failures instead of `raise ... from None`. Readers are terminated together with the owned process group on cleanup and interrupt. `DEVNULL` redirection is not used because it destroys diagnostics. No separate logging framework or second log store is introduced. (command-execution, server-lifecycle)
- **`module update` keeps the final traceback behind a long startup log (item 12)**: when a valid nonce-framed payload is present, `user_error` or `finalization_error` from the common shell wrapper is used with priority. When payload is missing or malformed, a bounded redacted tail of `stderr` is used instead of the first N characters. Full unlimited tracebacks are not emitted and existing redaction is not weakened. Rich, JSON, and TOON return the same stable error code and safe details. (odoo-module-workflow, cli-odcli)
- **`odcli --version` shows the installed VCS revision (item 13)**: the CLI reads optional PEP 610 `direct_url.json` via `importlib.metadata`. If `vcs_info.commit_id` is valid, the human version output appends the short commit, e.g. `odcli, version 0.1.0 (6a984c7)`. Wheel/sdist installs without `direct_url.json` keep the package version. Malformed or missing metadata safely falls back to the package version. The command stays fast, does not call Git, does not require a checkout or network, and does not import operation-only dependencies. (packaging, cli-odcli)
- **`odcli bug-report init/submit` and the `odcli-bug-report` skill (item 14)**: two new CLI leaves in a `bug-report` group manage local report drafts under `get_user_root()/bug-reports/<REPORT_ID>/` with `report.md`, `metadata.json`, and `reviews/1.json`..`reviews/3.json`. `PUBLIC_LEAF_CASES` records `sdk_primitive` `bug_report_init_command` and `bug_report_submit_command` (never `cli_only_reason`). `init` creates a UUID and a template, works offline from any cwd, and uses `0700`/`0600` permissions. `submit --dry-run` validates structure, required sections, size (`report.md` max 262144 bytes), and secret redaction, and shows the target repo, title, body, labels, and SHA-256. Submit is allowed when the last `reviews/N.json` (`N` in 1..3) is `approved` for the exact payload hash; three `changes_requested` stops without publish. There is no `--skip-review` or `--force`. `gh` is invoked through `internal/proc` with `shell=False` and `--body-file -` after an ActionStep that records submit intent. Defaults: repo `maximchikAlexandr/odoo-instance-sdk`, GitHub labels `["alpha-testing"]` only (`--kind` is not a label), configured in `get_config_root()/user.toml`. The child inherits `GH_TOKEN`; OdCLI does not copy it. Duplicate-issue handling is skill-only (show the user; do not auto-create). The skill writes `reviews/N.json`. Emergency unblock is skill-only. (bug-report [new], cli-odcli, sdk-package-imports)
- **Centralized HTTP transport behind `OdooHttpClient` (item 15)**: `src/odoo_instance_sdk/internal/transport/` holds one minimal base HTTP wrapper over `httpx` and exactly one subclass, `OdooHttpClient`, for existing Odoo HTTP endpoints. Resources depend on that internal client, not on `httpx`. CLI commands SHALL NOT import it. Each resource operation constructs and closes its own client. An architecture inventory allowlist is line-specific to files under that transport directory. Lazy import keeps `httpx` absent after `import odoo_instance_sdk.cli`. No retry/backoff. XML-RPC stays in `tests/integration/real_odoo/test_critical_path.py` via a test-support helper; no production `OdooXmlRpcClient`; `src/` SHALL contain zero `xmlrpc.client.ServerProxy` call sites. (transport-clients [new], database-management, environment-monitor)
- **`odcli update` safely upgrades a uv-tool install and applies migrations (item 16)**: `update_command()` is the `sdk_primitive` (never `cli_only_reason`). Default `--ref` is `main`. `--dry-run` never launches a process: Inspect is in-process ActionSteps; uv install and maintenance `odcli update` appear as frozen ProcessSteps. Mutating `already_current` without uv only when `--ref` is a 40-char SHA matching PEP 610. `--check` is the same leaf with `PublicLeafCase` variant `process-previewable-read-only` and may run uv `--dry-run` (no pip fallback). Maintenance is env `ODCLI_MAINTENANCE=1` on the existing `update` leaf, not a new Click command. Unfinished journal: `update` resumes; other commands fail `update_incomplete`. Lock `get_locks_dir()/odcli-update.lock`. Coordinator calls existing Alembic/`internal/storage_migration.py` steps; no second version scheme. Expression SHALL NOT appear in this flow. (self-update [new], cli-odcli, packaging)
- **E/F-quality tests are removed or rewritten without losing coverage (item 17)**: the list of E/F-grade tests and the reason for each grade are recorded. Each is rewritten, replaced by a behavioural test, or deleted as duplicate/implementation-coupled. Deletion preserves behavioural coverage elsewhere; "did not crash" is not accepted as a replacement assertion. Line and branch coverage do not drop below baseline; requirement and regression coverage is preserved; no new skips, xfails, or weakened assertions are added without justification. (packaging)
- **`run --detach` automatically provisions a separate logfile (item 18)**: one shared resolver computes the effective logfile: an explicit non-empty `logfile` in effective `odoo.conf` wins; otherwise `odoo.log` next to the effective `odoo.conf` is chosen, its parent directory and file are created before detached spawn, and the path is passed to Odoo by the standard argument mechanism without editing the user's `odoo.conf`. New isolated environments write an environment-owned `<environment-root>/odoo.log` into generated `odoo.conf` and create the file with the other artifacts. The same fallback applies to old/partial isolated configs. `run --detach`, `logs`, the structured result, and runtime metadata use one resolved path. Two isolated environments of one project use different logfiles. `--dry-run` shows the resolved path without creating the directory or file. Unwritable fallback fails before spawn with a clear message and the exact path. (server-lifecycle, cli-odcli, development-environment)

## Capabilities

### New Capabilities

- `bug-report`: The `odcli bug-report init/submit` CLI leaves, the local draft directory contract (`report.md`, `metadata.json`, `reviews/1..3.json`), the up-to-three independent reviewer rounds bound to a payload SHA-256, the `gh` submission boundary, the re-submission/duplicate/unknown-outcome contract, and the portable `odcli-bug-report` agent skill under `.agents/skills/`.
- `transport-clients`: The internal `httpx` wrapper, the single `OdooHttpClient` subclass, managed session lifecycle, test-only DI protocol, redacted logging, typed error conversion, no-retry, lazy import, and the line-specific `src/` httpx allowlist under `internal/transport/`.
- `self-update`: The `odcli update` command, nine phases, coordinator over existing Alembic/storage migrations, `odcli-update.lock`, snapshot/rollback/journal under `get_user_root()/update/`, `--check`/`--dry-run`/`--ref`/`--yes`/`--allow-downgrade`, typed outcomes, and `internal/proc` uv plus maintenance child.

### Modified Capabilities

- `cli-odcli`: `env rm` gains `--force-connections`; `postgres up` builds truthful diagnostic output; `init` gains `--test-url`/`--test-database`/`--test-branch`/`--local-config`/`--allow-partial`; `db reset-admin-password` and restore require an explicit secret via prompt or `ODCLI_ADMIN_PASSWORD`; `db refresh` resolves an optional `test_instance.database`; long restore shows real Rich stages and elapsed time; `module update` preserves the final traceback; `odcli --version` shows the 7-character VCS revision; `run --detach` provisions an effective logfile via `resolve_effective_logfile()` injecting `--logfile`; `bug-report` and `update` leaves record named `sdk_primitive` values and `e2e_disposition`.
- `server-lifecycle`: `run_foreground_command()` releases the artifact lock before waiting; auxiliary Odoo stdout/stderr are drained concurrently with a bounded redacted tail attached to readiness/startup failures; long-restore Rich stages and elapsed time are published through the existing `StepObserver`/`StepEvent`; `run --detach` provisions and uses the effective logfile.
- `instance-runtime-binding`: foreground runtime identity registration and cleanup remain under the artifact lock, but the wait happens outside it; PID/create-time/process-group validation and stale-runtime safety are preserved.
- `odoo-git-workflow`: `git commit` uses the already-resolved project ticket settings in environment worktrees and no longer re-loads `.odcli/project.toml` from the worktree root.
- `development-environment`: `env rm` routes `--force-connections` through `remove_command()` into `build_database_drop_command()` with COPY-only terminate scope; new isolated environments write an environment-owned `odoo.log` into generated `odoo.conf`; the self-contained `data_dir` is recorded for filestore provenance.
- `postgres-cluster`: `postgres up` builds its diagnostic result from the captured cluster even when the SDK call returns `None`.
- `environment-monitor`: a failed/empty/unparseable Docker metrics snapshot no longer implies `STOPPED`; lifecycle state comes only from `PostgresCluster.status_command()`; `stats_failed` degrades only metrics.
- `project-init`: `init` gains `--test-url`/`--test-database`/`--test-branch`/`--local-config`/`--allow-partial`, the blocking completeness check aligned with optional `test_instance.database`, the interactive cancel-vs-partial question, `init_incomplete` on `--no-input`, `.odcli/.env` under `0600`, `ODCLI_TEST_INSTANCE_ORIGIN_PINS`, `data_dir={project_root}/.odcli/filestore`, preservation of an existing `[test_instance]` on re-run, and Compose bootstrap database `tmp` with `base` installed.
- `backup-catalog`: large-backup validation removes the 512 MiB/2 GiB ceilings; keeps 4096 entries and 64 KiB streaming; ratio 100 never invalidates `dump.sql` alone; free-space reserve `max(1 GiB, 10%)`; operator key `backup.max_uncompressed_bytes` in `get_config_root()/user.toml`; error codes `backup_corrupt`/`backup_unsafe`/`backup_operator_limit`/`backup_insufficient_disk`; version from `version` else `major_version` + `.0`.
- `database-restore`: restore records the canonical project-owned `data_dir` in the binding; `db rm` deletes only the exact contained non-symlink filestore and returns `deleted`/`absent` with the path; the admin password reset is an explicit secret assignment shared by restore, COPY replacement, and `db reset-admin-password`.
- `database-backup`: remote refresh resolves the optional `test_instance.database` via `DatabaseResource.names()`; exactly one database is selected; zero/many databases produce distinct actionable errors; the auto-detected name is not written back to `project.toml`.
- `odoo-module-workflow`: `module update` prioritizes a valid nonce-framed payload and falls back to a bounded redacted tail of `stderr` so the final traceback is not lost behind a long startup log.
- `packaging`: `odcli --version` appends 7-character `commit_id`; E/F cleanup uses recorded heuristics and a decision table; architecture gates cover httpx allowlist, zero `ServerProxy` in `src/`, and self-update lock.
- `sdk-package-imports`: `bug-report` and `update` MUST set `sdk_primitive`; `cli_only_reason` is forbidden for them; `httpx` only under `internal/transport/`.
- `command-execution`: spawned long-running handles drain `stdout`/`stderr` concurrently with a bounded redacted tail; readers are terminated with the owned process group on cleanup and interrupt.
- `database-management`: all production HTTP calls to the Odoo origin go through `OdooHttpClient` (added requirement); `httpx` types/exceptions do not leak into public SDK/resource interfaces.

## Impact

- Affected implementation areas: `src/odoo_instance_sdk/cli.py`, `src/odoo_instance_sdk/commands/` (`env/`, `db.py`, `backup.py`, `pg.py`, `module.py`, new `bug_report.py` and `update.py`), `src/odoo_instance_sdk/resources/` (`instance/`, `environment/`, `monitor/`, `database/`, `postgres/`, `git.py`), `src/odoo_instance_sdk/internal/` (`proc/`, `doctor/`, `dbprep/`, `dbreplace/`, `cli_format.py`, new `transport/`, new `bug_report/`; update coordinator may live next to `internal/storage_migration.py` rather than a second registry package), `src/odoo_instance_sdk/storage/` (`catalog/`, `catalog_migrations/`), `src/odoo_instance_sdk/models/`, `pyproject.toml`, `README.md`, `docs/`, `.agents/skills/odcli-bug-report/`, `PUBLIC_LEAF_CASES`, and `tests/fixtures/architecture_inventory.py`. New mutating/spawning SDK operations expose additive `*_command()` siblings; CLI convenience methods delegate to them.
- Affected tests: foreground stop/lock regression, `git commit` ticket-URL regression, `env rm --force-connections` regression, `postgres up`/`env list` truthful-state regression, `init` self-contained setup and partial-setup gates, large-backup validation streaming and free-space preflight, self-contained restore filestore lifecycle, admin password reset secret boundary, optional `test_instance.database` resolution, long-restore Rich progress, auxiliary pipe drain, `module update` traceback preservation, `--version` VCS metadata, `bug-report init/submit` and skill scenarios, transport-client architecture gate, `odcli update` nine-phase and rollback scenarios, E/F test cleanup, and `run --detach` logfile provisioning.
- Public compatibility: existing CLI command names, exit codes, JSON envelope v1, redaction, and passthrough streams remain stable. Additive public types are `BugReportInitResult`, `BugReportSubmitResult`, `UpdateResult`, and optional `test_instance.database`. `OdooHttpClient` stays internal. `env rm` gains `--force-connections`; `init` gains new options; `db reset-admin-password` and restore require a secret where previously a hidden `admin` was assigned. Large backups that were previously rejected as invalid become valid; restore preflight gains a free-space check. `odcli --version` output may append a 7-character commit for VCS installs.
- Dependencies: no new runtime dependency is required for items 1–13, 17, 18. Item 14 reuses the existing `gh` boundary. Item 15 reuses the already-installed `httpx`. Item 16 reuses the existing `uv`/`subprocess` boundary and the existing Alembic/SQLAlchemy Core migration ledger introduced by #67. No new rendering, plugin, or framework dependency is introduced.
